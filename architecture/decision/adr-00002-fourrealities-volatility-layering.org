#+TITLE: ADR-002: FourRealities Volatility Layering and Service Contracts
#+DATE: 2026-11-01
#+STATUS: Proposed

* Status
Proposed - Pending owner approval, together with [[file:adr-00001-fourrealities-evidence-data-model.org][ADR-001]].

* Context

Asymm builds use IDesign volatility-based decomposition with explicit service-type contracts
([[file:/home/fahimfarookme/Documents/projects/m360/architecture/decision/adr-00029-service-type-contracts-marker-interfaces.org][M360 ADR-029]]):
Clients call Managers; Managers orchestrate Engines and Accessors; Engines hold all logic and
do no I/O; Accessors do all I/O; contracts are the firewall between volatility zones.

FourRealities runs on Atlassian Forge. The backend runtime is Node.js (=runtime: nodejs22.x=
in =apps/fourrealities/manifest.yml=), so the code is TypeScript. The pattern still applies;
only its form changes (TypeScript interfaces and folders instead of Maven modules).

The Part B build so far (branch =feature/fourrealities-research-build=, commit =7968c2e=)
already separates pure gate logic from Jira and KVS access, but it breaks the pattern in
five places (all Observed-code):

| # | Where | Violation |
|---+-------+-----------|
| 1 | =src/index.ts= | Client, Manager and Accessor in one file. It registers resolvers (Client), orchestrates (Manager), and calls =api.asUser().requestJira= and =kvs= directly (Accessor) in =getIssueAlignment=, =checkIssueScope=, =linkDecision=, =recordException=, =ForgeKvsProvider=. |
| 2 | =src/domain/gates.ts= imports =src/jira/dev-field.ts= | An Engine depends on the Jira access package. Parsing a value is logic; it belongs on the Engine side of the contract. |
| 3 | =src/ui/gate-text.ts= imports =RECOVERY_ORDER= from =src/domain/metrics-engine.ts= | The Client depends on an Engine implementation, not on contract data. |
| 4 | =src/snapshot.ts= | A Manager holds rules: the "keep the previous Intent result" rule and the trend-point calculation. |
| 5 | =src/index.ts= =resolveStorage= | A =NODE_ENV === 'test'= branch in production code chooses the storage. Wiring belongs in one composition point (the same defect class as LedgerSeal finding LS-14). |

* Decision

** 1. Four service types with contracts

** 2. Markers in TypeScript

TypeScript types are structural, so an empty marker interface matches every object. Each
marker therefore carries a literal discriminant:

#+begin_src typescript
/** Engines: all rules, pure input to output, no I/O, no @forge imports, no other Engine. */
export interface Engine { readonly serviceType: 'engine'; }
/** Managers: orchestration only, no rules, no I/O. */
export interface Manager { readonly serviceType: 'manager'; }
/** Accessors: all I/O (Jira REST, Forge KVS). The only importers of @forge/api and @forge/kvs. */
export interface Accessor { readonly serviceType: 'accessor'; }

export interface GateEngine extends Engine { evaluate(facts: IssueFacts, catalog: EvidenceCatalog): IssueGates; }
#+end_src

Implementations are named =Default<Name>= (for example =DefaultGateEngine=), as in M360.

** 3. Dependency rules, enforced by a test

An architecture test (=test/architecture.test.ts=) reads every source file and fails when:
- a file in =src/engine/= imports anything outside =src/contract/=;
- a file in =src/manager/= imports anything outside =src/contract/=;
- any file outside =src/accessor/= imports =@forge/api= or =@forge/kvs=;
- any file other than =src/index.ts= imports a =Default*= implementation;
- a file in =src/frontend/= or =src/ui/= imports from =src/engine/=, =src/accessor/= or =src/manager/=.

This is the TypeScript equivalent of the ArchUnit rule that M360 ADR-029 lists as open.

** 4. One composition point

=src/index.ts= builds the object graph once per invocation (accessors with the request
principal, engines, managers) and passes it to the resolver handlers. Tests build their own
graph with fake accessors. =resolveStorage= and its =NODE_ENV= branch are removed.

* Alternatives Considered

** Alternative A: Keep the current folders (domain, jira, storage)
- For: no refactor.
- Against: the five violations stay; nothing stops new ones.
- Verdict: Rejected.

** Alternative B: Layers without contracts (folders only)
- For: smaller change.
- Against: no firewall; Managers depend on concrete Accessors; tests keep mocking =@forge/api=,
  the mock that hid the =route= defect fixed in commit =9bbfa55=.
- Verdict: Rejected. Fake Accessors behind contracts let tests stop mocking the platform; the
  real =route= tag is then exercised only in Accessor tests.

* Consequences

** Positive
- Engines are tested with plain inputs; no platform mocks.
- Platform calls live in one place, tested against the real =@forge/api= =route= tag.
- The architecture test stops new layering defects at build time.
- Same vocabulary as M360.

** Negative
- A refactor of the code built so far (about 1,500 lines moved, not rewritten).
- More files and interfaces.

** Mitigations
- The refactor is one backlog item with no behaviour change: the existing 205 tests must stay
  green, apart from moving to fake Accessors.
- It lands before the ADR-001 model changes, so those changes are made once, in the new layout.
