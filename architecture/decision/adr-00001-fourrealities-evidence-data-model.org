#+TITLE: ADR-001: FourRealities Evidence Data Model Patterns
#+DATE: 2026-11-01
#+STATUS: Approved

* Status
Approved - 2026-11-01 by the owner, in chat, with Option C for the approval rule (see "Options considered").
Implemented: B-30 (Patterns 3 and 5), B-31 (Patterns 2 and 4; per-project override not yet), B-32 (Pattern 6).

* Context

FourRealities shows, for each Jira issue, whether four kinds of delivery evidence exist
(Intent, Process, Code, Audit) and where each fact comes from. The model in specification v2
(=docs/spec/fourrealities-spec-v2.md=) was designed item by item during the build. It was not
checked against the enterprise data model patterns that Asymm applies elsewhere
([[file:/home/fahimfarookme/Documents/projects/m360/architecture/decision/adr-00009-data-model-patterns.org][M360 ADR-009]]).

A review against those patterns found three gaps that matter for an evidence product:

1. *Exceptions have no history.* A new Code exception overwrites the earlier one
   (=src/index.ts= =recordException=, KVS =fr:issue:{id}:exception=). An audit trail cannot be
   rebuilt.
2. *The requester approves their own exception.* One person records the exception, and the
   gate shows "Excepted" at once. This is self-approval. Audit guidance ranks inquiry below
   observed evidence (ISA 500, research EV-01) and asks for separation of duties
   (NIST SP 800-53 AC-5, research EV-03).
3. *Evidence rules are hard-coded.* The Intent rule matches a fixed list of issue-type names
   (=src/domain/gates.ts= =INTENT_ISSUE_TYPES=). A team that records decisions another way must
   change the code.

Two facts constrain the design:
- *Jira owns the work data.* Issues, links, status history, people and Confluence pages
  belong to Atlassian. FourRealities reads them and never copies them as its own facts.
- *Forge KVS is a key-value store.* No joins, 240 KiB per value, 25 operations per
  transaction (research FL-01). A logical model must map onto keys, not tables.

* Decision

Apply the following patterns. Each pattern names what Jira owns (read only) and what
FourRealities owns (written by FourRealities).

** Pattern 1: Work Effort, Association and Content (Silverston)

*Source*: Len Silverston, "The Data Model Resource Book" Vol 1 (Work Effort). Verified against
the Apache OFBiz implementation of that model (=workeffort-entitymodel.xml=, read 2026-11-01).

*** Pattern Description
- *WorkEffort*: a unit of work (task, project, phase).
- *WorkEffortAssoc*: a typed, time-bounded link between two work efforts
  (=workEffortIdFrom=, =workEffortIdTo=, =workEffortAssocTypeId=, =fromDate=, =thruDate=).
- *WorkEffortContent*: a typed, time-bounded link from a work effort to content
  (=workEffortContentTypeId=, =fromDate=, =thruDate=).
- *WorkEffortStatus*: status history (=statusId=, =statusDatetime=, =setByUserLogin=, =reason=).
- *WorkEffortPartyAssignment*: a party in a role on a work effort, time-bounded.

*** Application to FourRealities (all owned by Jira, read only)
#+begin_src text
SILVERSTON (OFBiz)              JIRA CLOUD                         FOURREALITIES USE
──────────────────              ──────────                         ─────────────────
WorkEffort                      Issue                              subject of every observation
WorkEffortType                  Issue type                         classifies the link target
WorkEffortAssoc + AssocType     Issue link + link type             Intent evidence (decision issue)
WorkEffortContent + Type        Remote link + application type     Intent evidence (Confluence page)
WorkEffortStatus (history)      Status changelog                   rework loops, started, done
WorkEffortPartyAssignment       Assignee                           separation-of-duties check
#+end_src

*** Key Decision
Intent evidence is decided by the *type of the association* and the *type of the target*,
both read from a Knowledge Level catalog (Pattern 4), never by titles and never by a fixed
list in code. Default: a Confluence content link on this site, or an issue link to an issue
whose type is a decision or specification type (the current rule, moved into the catalog).

*** Trade-offs
- Jira link-type names differ per site. The catalog must be editable per project
  (a settings page is a later backlog item; defaults ship in code).

** Pattern 2: Observation and Measurement (Fowler)

*Source*: Martin Fowler, "Analysis Patterns", Ch. 3. Same pattern as M360 ADR-009 Pattern 3.

*** Pattern Description
- *Observation*: a recorded fact about a subject, at a time, by an observer, with a method.
- *Phenomenon*: what is observed.
- *Measurement*: a quantified observation. Derived measurements are computed, not recorded.

*** Application to FourRealities (owned by FourRealities, derived)
#+begin_src text
GATE_OBSERVATION
├── subject           ─── Jira issue id
├── phenomenon        ─── gate: INTENT | PROCESS | CODE | AUDIT
├── value             ─── state: FOUND | MISSING | EXCEPTED | NEEDS_RECHECK | NOT_APPLICABLE
├── method            ─── evidence source (catalog): e.g. LEDGERSEAL_PROPERTY
├── verification      ─── VERIFIED | NOT_VERIFIED | HEURISTIC   (protocol strength)
├── evidence_ref      ─── what was seen: link key, page title, certificate id, PR count
├── reason            ─── reason code (UI text)
└── observed_at       ─── snapshot or read time

DERIVED MEASUREMENTS (computed on read, never stored as facts)
├── RAI per issue     ─── share of FOUND among FOUND + MISSING
├── gate rates        ─── per project, with numerator and denominator
└── TREND_POINT       ─── weekly aggregate of observations (stored, bounded to 52)
#+end_src

*** Key Decision
Add =method= (evidence source) and =evidence_ref= as fields of the observation. Today the
source is inferred from the reason code (=src/ui/gate-text.ts=), which ties the UI text to
the evidence source. RAI stays a derived measurement (research H5).

*** Trade-offs
- Row size grows by a few bytes per gate. Measured headroom: 63,099 B per 100-row chunk
  against a 100 KiB budget (harness T-06).

** Pattern 3: Status with History and Valid Transitions (Silverston)

*Source*: Silverston Vol 1 status entities; OFBiz =WorkEffortStatus=, =StatusItem=,
=StatusType= and =StatusValidChange= (=statusId=, =statusIdTo=, =conditionExpression=,
=transitionName=), read 2026-11-01.

*** Pattern Description
- Status is a history, not a field. Each change records who, when and why.
- A catalog lists the valid transitions and the condition for each.

*** Application to FourRealities (owned by FourRealities)
A Code exception becomes a *gate exception* with a lifecycle:
#+begin_src text
EXCEPTION_STATUS (Knowledge Level)        VALID_TRANSITION (Knowledge Level)
├── REQUESTED                              REQUESTED ──approve──> APPROVED   [by APPROVER: project administrator, not requester, not assignee]
├── APPROVED                               REQUESTED ──reject───> REJECTED   [by APPROVER]
├── REJECTED                               REQUESTED ──withdraw─> WITHDRAWN  [by requester]
├── WITHDRAWN                              APPROVED  ──revoke───> REVOKED    [by APPROVER]
└── REVOKED

GATE_EXCEPTION_EVENT (Operational Level, append-only)
├── issue_id, gate                         ─── subject
├── status                                 ─── new status
├── at                                     ─── event time
├── by_account_id, as_role                 ─── who, in what role (Pattern 5)
└── reason                                 ─── why
#+end_src

The gate shows *Excepted* only while the current status is APPROVED. While REQUESTED, the
gate stays *Evidence missing* and the panel shows "Exception requested by <user>, awaiting
approval". A pull request that appears later ends the exception's effect (existing rule).

*** Key Decision
Store each event under its own KVS key (append-only), never rewrite an event:
=fr:ex:{issueId}:{gate}:{at}:{seq}=. The current status is the last event. The issue
property =fourrealities-exception= holds only the current status summary, for other tools.

*** Trade-offs
- Reading the current status needs a prefix query per issue on the panel (one query), and
  one prefix query per project page of 100 events in the snapshot build.
- The number of event keys grows with use, but each value is small and no value grows.

** Pattern 4: Knowledge Level / Operational Level (Fowler)

*Source*: Fowler, "Analysis Patterns". Same pattern as M360 ADR-009 Pattern 2.

*** Application to FourRealities
#+begin_src text
KNOWLEDGE LEVEL (catalog, defaults in code,      OPERATIONAL LEVEL (instances)
later per-project override in KVS)
────────────────────────────────────────         ─────────────────────────────
GATE_TYPE (4) + applicability rule               GATE_OBSERVATION
EVIDENCE_SOURCE (catalog of sources,             GATE_OBSERVATION.method
  each with its verification class)
INTENT_EVIDENCE_RULE (link types, target         GATE_OBSERVATION for INTENT
  issue types, content application types)
EXCEPTION_STATUS + VALID_TRANSITION              GATE_EXCEPTION_EVENT
ROLE_TYPE (REQUESTER, APPROVER)                  GATE_EXCEPTION_EVENT.as_role
#+end_src

*** Key Decision
One catalog module holds every rule as data. Gate functions read the catalog; they hold no
lists of names. A per-project override key (=fr:p:{key}:catalog=) is reserved; the settings
page that writes it is a separate, later backlog item.

** Pattern 5: Party Role and Accountability (Silverston, Fowler)

*Source*: Silverston Vol 1 Ch. 2; Fowler "Analysis Patterns" Ch. 2; M360 ADR-009 Patterns 1 and 5
and the Party-Role deep dive (explicit role context).

*** Application to FourRealities
Jira owns the parties (Atlassian accounts). FourRealities records the *role context* of each
action explicitly on the event (=as_role=), as M360 does with PartyRole-to-PartyRole:
"acc-1 *as REQUESTER* asked; acc-2 *as APPROVER* approved".

Approval rule (Knowledge Level, on the APPROVE, REJECT and REVOKE transitions; Option C):
- The approver holds the Jira project permission =ADMINISTER_PROJECTS= in the issue's project,
  or the global Jira permission =ADMINISTER= (owner decision "1B", 2026-11-01, after the live
  check found a Jira administrator without project administration refused on AUDT).
  Checked as the approving user in one call:
  =GET /rest/api/3/mypermissions?projectKey={key}&permissions=ADMINISTER_PROJECTS,ADMINISTER=
  (granted when either =havePermission= is true). Scope =read:jira-work=, which the app
  already holds; no new scope. Verified in the Jira Cloud OpenAPI document
  (=swagger-v3.v3.json=, read 2026-11-01): operation "Get my permissions", scope state "Current".
- The approver is not the requester (separation of duties; without it an administrator could
  approve their own request).
- The approver is not the issue's assignee at approval time.
- Jira's own Edit Issues permission is enforced by the property write, made as the user.

*** Trade-offs
- In a project with one administrator, that person cannot approve their own request, and no
  one else can approve it. The panel says so plainly ("No other project administrator can
  approve this request").
- One extra Jira read per approval action.

** Pattern 6: Notes (Silverston)

*Source*: OFBiz =WorkEffortNote= (=noteId=, =internalNote=) over =NoteData=.

*** Application to FourRealities
A rework reason is a *note*, not an exception and not a status: an append-only list per
issue (=fr:note:{issueId}:{at}:{seq}=), with author and time. It never changes a gate.

* Consequences

** Positive
- Every exception decision has a full, append-only trail: who asked, who approved, when, why.
- No one can turn their own gate to "Excepted" (separation of duties).
- Evidence rules change by data, not by code.
- The observation carries its own source and reference, so the UI text no longer encodes
  where evidence came from.
- The same vocabulary as M360 (Party Role, Knowledge Level, Observation, Status history).

** Negative
- A project administrator other than the requester and the assignee is needed for every
  Code exception. Small teams may find this slow, and a one-administrator project cannot
  approve that administrator's own requests.
- More KVS keys and one more prefix query on the issue panel.
- Migration: v2 exception records (one record per issue) become events.

** Mitigations
- The panel shows a pending request clearly, with the requester and reason, so an approver
  can act in one click from the same panel.
- Migration reads a v2 record as one REQUESTED event plus one APPROVED event by the same
  person, flagged =migrated: true=, and the panel labels it "approved before two-person
  approval was required". Nothing is deleted.
- Options A and B were considered and not chosen (see below).

* Options considered for the approval rule

| Option | Rule | For | Against | Outcome |
|--------+------+-----+---------+---------|
| A | Two people: requester and a different approver who is not the assignee | Meets separation of duties (EV-03) | Any colleague can approve | Not chosen |
| B | One person, with append-only history | No extra step | Self-approval stays; weak evidence (EV-01) | Not chosen |
| C | Approver is a project administrator, and not the requester or assignee | Strongest; the Jira permission read is supported with the existing scope | Needs an administrator for every exception | *Chosen (owner, 2026-11-01)* |

* Pattern Summary Table

| Pattern | Entities | Owner | Purpose |
|---------+----------+-------+---------|
| Work Effort, Assoc, Content | Issue, issue link, remote link, changelog, assignee | Jira (read only) | Inputs to the gates |
