#+TITLE: ADR-017: LedgerSeal Multi-Step Approval Routes
#+DATE: 2026-11-08
#+STATUS: Accepted

* Status
[ACCEPTED: 2026-11-08 by the owner, option A, with the defaults in "Owner decisions" below.]

Spec: =docs/spec/ledgerseal-spec-v4.md= section 15 (with 18 for the open questions). Related: ADR-016 (signing credential), ADR-018 (signing on the transition screen).

* Context
Today one seal is one signature. Any approver (project admin, Jira admin or a member of the
approver groups, spec v3 section 7.1) seals, and a different approver approves later changes
(section 7.2). There is no path such as "QA, then Regulatory", no group per step and no quorum.

The gap research (=docs/launch/research/dc-migration-gap-2026-11.md=, section 2 and section 4 rank 2)
lists Data Center apps without a cloud version whose need is approval routing: Deviniti "Approvals
- Advanced Issue Acceptance" (151 installs) and Globo "Issue Approval" (64). Their feature lists
were not read (research open point 3), so this ADR does not claim parity with them. It designs what
regulated teams commonly need: ordered or parallel stages, a group per stage, "any one" or "N of
the group", separation of duties across stages, and rejection.

Constraints from the current design:
- The hash chain, the snapshot canonical form and the evidence format are public through the open
  verifier (=asymmsystems/jira-governance-code-cli=, release v1.3.0; copy in =tools/verifier=).
  Evidence made today must still verify, and an old verifier must never PASS something it does not
  understand.
- The verifier's check 4 maps the newest row that is not =LS_REDACTED= to the attestation status
  (=LS_SEALED=, =LS_CHANGED=, =LS_REVOKED=). Any new status id in the newest row makes v1.3.0 FAIL.
- FourRealities reads the =ledgerseal-cert= property. It requires =status=, a UUID
  =certificateId=, =snapshotHash= and =sealedAt=, treats =SEAL_VALID= as sealed and
  =SEAL_BROKEN= or =SEAL_COMPROMISED= as broken, and any other status as "other"
  (=apps/fourrealities/src/engine/default-gate-engine.ts=, =isLedgerSealShape= and lines 288 to 296).
- Forge workflow validators get =transition.from.id= and =transition.to.id= and can have a
  configuration, but "Adding validator configuration with UI Kit is currently not supported"
  (jira-workflow-validator manifest page, 2025-03-12). LedgerSeal is UI Kit only.
- Jira Service Management approval steps "bypass workflow validators" (Atlassian KB).

* Options considered
** A. Stages on one seal: a route run collects stage signatures over one snapshot
A route is an ordered list of stage groups; stages in one group run in parallel. Each stage
signature signs the same snapshot hash. When the last group reaches quorum, the final signature
writes the seal (=LS_SEALED=) and names every stage signature. A covered change or a rejection
ends the run, and a new run starts at the first group.
- For: one certificate per approval, as today; the validator, change detection and the evidence
  keep their meaning; the verifier can check quorum and separation of duties from the history.
- Against: new row types in the chain and a new evidence format; more resolver logic.
** B. One full seal per stage
Each stage writes its own seal and certificate; the validator checks the seal of the stage it
gates.
- For: little new logic per seal.
- Against: several "current" certificates per issue; a QA seal and a Regulatory seal could cover
  different content unless more rules are added; the property and FourRealities see only one; the
  verifier cannot tell a finished route from a half one.
** C. Leave routing to Jira workflow statuses
Each workflow status is a stage; a Jira condition limits who may transition; LedgerSeal seals at
each gate.
- For: almost no new code.
- Against: no quorum, no separation of duties across stages, nothing in LedgerSeal's evidence that
  shows the route; it depends on each customer's workflow being right.
** D. Use Jira Service Management approvals
- Against: JSM only; approval steps bypass validators; the approval is not bound to the content.

* Owner decisions (2026-11-08)
The owner approved option A and told the developer to use the spec's recommended default for each
open question that he did not answer himself:
- *Q-06 (approval of changes after a routed seal):* the full route again, by default; a route may
  name a shorter re-approval list of stages (decision 7).
- *Q-07 (route edited while a run is open):* the run stays pinned to the route version of its first
  signature (decision 3).
- *Q-08 (who may edit routes):* Jira admins only.
- *Q-09 (verifier version for format 2):* 1.4.0, because no existing result changes (decision 13).
- *Q-11 (group names in the evidence):* included; group names are not personal data.
- *Q-15 (new, FourRealities):* the one-line FourRealities change is part of this work: a
  =ledgerseal-cert= property with no =status= reads as "not sealed", not as "shape unknown".
- When Part 11 signing (ADR-016) is on for the project, each stage signature and each rejection
  needs the emailed single-use code of ADR-016 decision 2.

* Decision (accepted 2026-11-08)
Adopt option A.

1. *Route.* A route has 1 to 8 stages in 1 to 8 order groups. A stage has a name, a meaning
   (=LS_APPROVER=, =LS_REVIEWER=, =LS_VERIFIER=), 1 to 10 approver groups, and a quorum: "any one"
   or "N of the group" (N from 1 to 10, counting distinct people). Stages in one order group may
   be signed in any order; the next group opens only when every stage of the current group has
   its quorum.
2. *Scope.* A Jira administrator binds a route to a project and to issue types (or all issue types
   of that project) on the admin page. The most specific binding wins (issue type over "all").
   With no binding, the implicit default route applies: one stage, quorum "any one", approvers as
   in spec v3 section 7.1. This is exactly today's behaviour.
3. *Versions.* Every save of a route makes a new immutable route version with a =routeHash= (the
   SHA-256 of its canonical JSON, spec v3 section 4.1 rules). A run is pinned to the version in use
   at its first signature. Editing a route does not change running runs (open question Q-07).
4. *Separation of duties.*
   - A person signs at most one stage in a run.
   - A person who changed covered content since the last seal cannot sign any stage of the run that
     approves those changes (the spec v3 section 7.2 rule, extended to every stage).
   - Membership is checked as the user at signing (=/rest/api/3/myself?expand=groups=); the group
     that qualified the signer is recorded in the row.
5. *Rejection.* A person allowed to sign an open stage may reject, with a reason (1 to 500
   characters). The run ends; its signatures stay in the history as a permanent record (preamble
   comment 127: signatures "must remain a permanent part of the record") but count for nothing. The
   next signature starts a new run at the first group.
6. *Change during a run.* A covered change voids the run (all its signatures signed another hash).
   This is recorded as a "run voided" row, not as an incident: no seal was broken, so
   =everCompromised= does not change. If a seal exists, the existing incident rules still apply.
7. *Approval of changes after a seal.* A change after a seal is approved by a full new run of the
   route (default). A route may name a shorter "re-approval" list of stages (open question Q-06).
8. *Revoke.* Unchanged, except that in a routed issue the revoker must be allowed to sign a stage of
   the route's last order group. A revoke applies to a seal, as today; when a seal exists, revoking
   it also ends an open run. With no seal, a run ends only by rejection or by a covered change.
9. *Seal state stays separate from run state.* The seal state machine of spec v3 (=LS_SEALED=,
   =LS_CHANGED=, =LS_REVOKED=) is unchanged. Run rows get their own status ids:
   =LS_RUN_SIGNED= (transition =SIGN_STAGE=), =LS_RUN_REJECTED= (=REJECT=), =LS_RUN_VOIDED=
   (=VOID=). The final stage signature is the =LS_SEALED= row itself (=SEAL= or =RESEAL=); its data
   lists the entry hashes of the run's other signature rows and the route version and hash.
10. *Default route makes no run rows.* With the implicit route, a seal writes exactly the rows it
    writes today, so existing evidence and new single-stage evidence look the same.
11. *Validator.* The gate passes only for a completed seal that is unchanged, as today. A stage may
    name target statuses it gates (for example "QA approved"): a transition to such a status passes
    when that stage, and every stage before it, has its quorum in the open run or the seal. The
    validator reads =transition.to.id=, so no validator configuration screen is needed.
12. *Attestation.* Schema 4 adds an =approval= object (=runState=, =stagesComplete=,
    =stagesTotal=, =routeHash=). =status= keeps its four values and meanings. Before the first seal
    the property has no =status= and no =certificateId=. A new index path =approval.runState=
    (alias =ledgersealApproval=) lets JQL find issues waiting for approval.
13. *Evidence and verifier.* Evidence with route data uses =format: "ledgerseal-evidence/2"= and
    includes the route version it was checked against. Verifier 1.4.0 checks the route hash,
    quorum, group order, one stage per person, and that every stage signature signed the sealed
    snapshot. It skips run rows when it compares the newest state with the attestation, as it
    skips =LS_REDACTED=. Evidence of format 1 gives the same result as in v1.3.0.
14. *Migration.* Nothing is rewritten. Existing seals stay valid with no route. A route applies to
    the next signature on an issue after it is bound. An issue sealed before the binding stays
    sealed; its next approval of changes uses the route.
15. *Part 11 mode.* When ADR-016's mode is on, every stage signature and every rejection needs the
    signing credential.

* Fix round 1 (2026-11-08, independent review of 427f6c9)
Decision 4 ("one person, one stage") did not hold when one person signed two stages at the same
moment, and the run record could lose a signature (H-1). Every flow that changes a run now holds a
per-issue run lock (=ls3:runlock:{issueId}=, created once; a lock older than 60 seconds is taken
over by one caller only). Under the lock the flow reads the run again and repeats its decisions:
the stage is still open, the person signed no other stage of the run, the run still holds the
snapshot the person signs, and it has not ended since the checks. The panel's "Reject" button
follows the same "one person, one stage" rule (L-6). The other half of L-6 is by design (decision
5 and spec 15.5): a rejection blocks the gated transitions until a new run starts, even when the
issue has a valid seal.

* Build results (2026-11-08, branch =feature/ledgerseal-regulated=)
Built as decided, development 6.7.0 to 6.12.0. Live on development (LSP-7, route bound to project LSP and
then unbound): a rejection with a reason ended the run, the next signature started a new run and sealed
the issue; the property became schema 4 with =approval.runState= =COMPLETE=; the exported evidence (format
2) passed the format 2 checks. Choices made while building, recorded here:
- A route is edited on the admin page as JSON (=name=, =stages=, =reapprovalStageIds=), checked field by
  field by the server; group and status names come from Jira. A form per stage can replace it later.
- The binding for every issue type is stored under the KVS key suffix =all=: =*= is not a valid KVS key
  character (live finding).
- The seal row of a route records =requiredStageIds= so an outside verifier can check the quorum of a
  re-approval run.
- The signature field on the transition screen (ADR-018) does not sign route stages; on a routed issue it
  points to the panel.
- The FourRealities change is the narrow form: a property of schema 4 with no =status= reads as "not
  sealed"; any other shape without a status stays "shape not written by LedgerSeal".

* Consequences
** Positive
- Closes the "no multi-step approval" gap stated in the gap research, with evidence an auditor can
  recheck offline, including quorum and separation of duties.
- Supports 11.10(f) "operational system checks to enforce permitted sequencing of steps".
- No change for customers who bind no route.
** Negative
- Verifier v1.3.0 FAILs evidence whose newest row is a run row (an issue still in approval). It
  never gives a false PASS. A completed routed seal PASSes in v1.3.0, but v1.3.0 does not check the
  route; the user guide must say "use 1.4.0 or later for routed evidence".
- FourRealities needs a small change: a property with no =status= means "not sealed" (today it
  would read as "shape unknown").
- The sealed issue record grows (route reference and stage counts): its size budget goes from
  under 4 KiB to under 16 KiB.
- An admin page section for routes, and more resolver paths to test.

* Considered and excluded
| Option or item | Why excluded |
|---|---|
| B. One seal per stage | Several current certificates; content of stages can differ; verifier cannot tell a finished route |
| C. Workflow statuses as stages | No quorum, no cross-stage separation of duties, nothing in the evidence |
| D. JSM approvals | JSM only; approval steps bypass validators; not bound to content |
| Weighted votes, "majority of group" | Not asked; "N of the group" covers the stated need |
| Delegation ("sign on behalf of") | Preamble comment 127: substituting another person's signature is falsification. A person signs only as themself |
| Automatic escalation, reminders by email | Needs a notify or write scope on every stage; not needed for the control. Later, if asked |
| Validator configuration screen | Custom UI only, a second UI technology; the stage's target statuses on the admin page do the same |
| Project admins editing routes | Kept to Jira admins first (open question Q-08) |
| Re-signing old evidence into the new format | Would rewrite the chain; old evidence stays format 1 |
