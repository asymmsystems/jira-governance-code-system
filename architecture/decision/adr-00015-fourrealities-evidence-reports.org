#+DATE: 2026-11-08

* Status
Accepted, 2026-11-08. The owner approved this ADR, the specification delta and the high-level design
(=architecture/model/fourrealities-evidence-report-hld.org=) on 2026-11-08, with all nine
recommendations of the HLD, section 11. The decisions are recorded verbatim in "Owner decisions"
below. The delta is merged into the full specification =docs/spec/fourrealities-spec-v4.md=;
=docs/spec/fourrealities-spec-v3.md= is frozen. The changes that the spikes made necessary are in

* Owner decisions (2026-11-08)
All nine recommendations of the HLD, section 11, are approved. The owner's words:
- Q1 Option C.
- Q2: only project or Jira admins plus a configured group create reports.
- Q3: retention 400 days by default, 90 days to 7 years.
- Q4: free-text fields show "changed" plus length only.
- Q5: use Forge Object Store (Preview), with the costed fallback.
- Q6: 200 reports per project, 50 MB per file.
- Q7: listing wording "evidence reports for change-management audits", never "audit log".
- Q8: Jira admins may delete a report early, with a reason and a record left in its place.
- Q9: when the licence is inactive, viewing and downloading existing reports keep working, but no new reports are made.
- Invariant 11 (decided later on 2026-11-08, after review round 2): "Sign, list them". When Jira cannot return an in-scope issue (deleted, moved, or not readable), the report is still signed and names every missing issue with its key and the reason, in the verifier output, the UI and the CSV; a report is never refused for this (spec v4, invariant 11 and D-19).

* Context

** Why now
The gap research (=docs/launch/research/dc-migration-gap-2026-11.md=, section 2 and section 4 rank
5) lists "Auditor for Jira" by Enhancera as a Data Center and Server app with no cloud version
(148 installs, migration path UNKNOWN). It names FourRealities as our cover and states the limit:
"Not a general Jira audit log". This ADR decides what FourRealities adds, and what it does not, so
that a regulated team that leaves Data Center can answer its change-management auditor in Jira Cloud.

** What change-management auditors ask
- *SOC 2, CC8.1* (AICPA 2017 Trust Services Criteria, revised points of focus 2022): "The entity
  authorizes, designs, develops or acquires, configures, documents, tests, approves, and implements
  changes to infrastructure, data, software, and procedures to meet its objectives." Points of focus
  include processes to authorize, document, track, test, approve and deploy changes, and to provide
  changes in emergency situations. Source: the criterion and point-of-focus wording as quoted by
  KirkpatrickPrice, https://kirkpatrickprice.com/tag/soc-2-academy/page/4/ (read 2026-11-08). The
  AICPA PDF itself needs a login, so it was not read. A Type II report covers a period, usually 6 to
  12 months, and the auditor samples changes from that period.
- *ISO/IEC 27001:2022, A.8.32 Change management*: changes to information processing facilities and
  information systems are subject to change management procedures. Guidance (secondary source,
  UpGuard, https://www.upguard.com/compliance/iso-27001/8-32.md, read 2026-11-08): log "the request,
  risk assessment, approval, testing results, deployment timestamp, and post-implementation
  status"; emergency changes "still require retrospective documentation".
- *ISO/IEC 27001:2022, A.8.15 Logging*: logs of activities, exceptions, faults and other relevant
  events are produced, stored, protected and analysed. Guidance (UpGuard,
  https://www.upguard.com/compliance/iso-27001/8-15.md, read 2026-11-08): a user id, a UTC time and
  an event type per entry; protection "from tampering, unauthorized access, and deletion";
  retention set by legal and forensic needs, with both a minimum and a maximum.
- The ISO texts are paid documents and were not read. The wording above is a paraphrase from the
  secondary sources named, not the normative text.

What these mean for a Jira team: for a sample of changes (issues) in the audit period, show who asked
for it, the intent, the approval, the test or Definition of Done, the code, the deployment, and who
changed what and when, in a form that the auditor can keep and that shows it was not edited later.

** Constraints
- Runs on Atlassian; the manifest declares no external egress (spec v3, invariant 8).
- Read as the user, with a Browse projects check as the user, before any read as the app
  (Uniform Permission Management Standard, invariant 1; spec v3, invariant 7).
- FSRT and Semgrep CI gates (=.github/workflows/fsrt.yml=, =.github/workflows/sast.yml=); every
  =/mypermissions= call is a direct =await api.asUser().requestJira(route`...`)= (FSRT report,
  =docs/security/fsrt-scan-2026-11-07.md=, section 4.4).
- Personal data: store account ids only where a rule needs them, report them weekly, erase closed
  accounts (ADR-014).
- Layering (ADR-002): Engines pure; Accessors the only I/O; Managers orchestrate; one composition
  point.
- ADR-001: "Jira owns the work data ... FourRealities reads them and never copies them as its own
  facts."
- Forge limits (checked 2026-11-08): UI invocation 25 s; scheduled trigger and async event consumer
  up to 900 s; memory up to 1,024 MB; resolver response 5 MB; KVS value 240 KiB, 25 operations per
  transaction; Object Store (Preview) objects up to 1 GB, pre-signed URL valid 1 hour, data residency
  enabled and meets the Runs on Atlassian storage criterion; Forge SQL 1 GiB per production install.
  Sources: =https://developer.atlassian.com/platform/forge/limits-invocation/= (updated 2026-09-01),
  =.../limits-kvs-ce/= and =.../limits-object-store/= (updated 2026-09-28), =.../limits-sql/=
  (updated 2025-12-01), =.../storage-reference/object-store/= (updated 2026-09-28),
  =.../runs-on-atlassian/= (updated 2026-08-24).

** 2. What FourRealities owns
FourRealities adds *evidence reports*: for one project and one date range, a report of the issues
in scope, each with its four gate observations, the references to the DefinitionGuard and LedgerSeal
records it verified, its own Code exception events and rework notes, and the Jira changelog entries
in the range (who changed which field, when, from what to what), filtered by user and field when
asked. This fits the product's purpose, "delivery evidence per issue", one level up: a project and a
period.

1. *Formats.* Each report is one JSON file (the full record) and one CSV file (one row per change,
   for spreadsheets), plus a signed manifest that holds the SHA-256 of both files.
2. *Signed.* FourRealities signs the manifest with Ed25519 under its own key (=fr-prod-2026-11=
   in production), the scheme LedgerSeal already uses (spec v3, section 8). The open verifier
   (=jira-governance-code-cli=) gains a command that checks the signature and both file hashes
   offline. A report also holds the hash of the project's previous report, so a removed report
   shows as a break in the chain.
3. *Stored in the app, not sent.* Reports are kept in Forge Object Store and listed on the project
   page. A user downloads a file through the UI. Nothing is sent out (no egress, no e-mail, no
   webhook).
4. *Scheduled reports.* A project administrator may set a weekly or monthly schedule. The daily
   trigger builds the report for the period that ended and stores it for download. "Scheduled"
   means stored in the app, never sent.
5. *Retention.* A Jira administrator sets how long reports are kept: default 400 days, at least 90
   days, at most 7 years. This retention applies to FourRealities reports only. FourRealities does
   not mirror Jira's history and does not extend Jira's own retention.
6. *Reads.* The issue set of an on-demand report comes from a JQL search *as the requesting user*,
   after a Browse projects check as that user. The long read of changelogs then runs as the app,
   only for those issue ids, in a queued job. A scheduled report reads as the app, and its download
   is allowed only to a user who can browse every issue in it (checked as the user at download time).
   No user ever receives an issue they cannot browse.
7. *Personal data.* A report holds no names and no raw account ids: it holds per-site keyed party
   tokens, as LedgerSeal does (ADR-011). At download, FourRealities builds an unsigned
   "people" file that maps tokens to account ids and display names, read as the downloading user.
   On account closure the token map entry is removed, so the signed files never change. The weekly
   personal data report (ADR-014) adds the accounts in the token map.
8. *Who may create a report.* Tier 1 of the permission standard (Administer projects in the
   project, or Administer Jira) or a member of an "evidence report" group set on the admin page
   (Tier 2), plus Browse projects. (Decided: Q2.)

** 3. What belongs to LedgerSeal or DefinitionGuard
- The hash-chained history of sealed content, its incidents, reseals and revokes, and the per-issue
  evidence export with the open verifier, stay in LedgerSeal. FourRealities cannot read
  LedgerSeal's app storage (each Forge app has its own) and must not copy its facts. A report
  references the seal by =certificateId=, =snapshotHash=, =status=, =sealedAt=, =keyId= and the
  verification result, so the auditor can fetch the LedgerSeal evidence for a sampled issue and
  check it with the same verifier.
- The Definition of Done history stays in DefinitionGuard; the report references =headHash=,
  =stateVersion=, =issuedAt= and the verification result.
- A project-level bulk LedgerSeal evidence export is a LedgerSeal backlog item, not part of this
  ADR.

** 4. Out of scope
See "Considered and excluded" below.

* Options

** Option A: No change; point to native features and LedgerSeal
- For: no work; no new storage, no new personal data.
- Against: N3 to N7 stay open. The migrating team still opens issues one by one for the auditor's
  sample, which is the problem our listing names.

** Option B: Synchronous export in the dashboard (CSV and JSON shown or copied, not stored)
- For: small; reads as the user only; nothing stored.
- Against: a resolver call has 25 s and a 5 MB response, so it fits small projects only. No record
  outlives the issue (N5), no schedule (N7), and no signature the auditor can check later unless the
  file is also signed (N4).

** Option C: Stored, signed evidence reports built by a queued job (chosen, recommended)
- For: closes N3 to N7; bounded by design (see the HLD, section 9); reuses the signing scheme, the
  verifier and the party token pattern of LedgerSeal; stays inside FourRealities' purpose.
- Against: new storage (Object Store, in Preview), a new signing key, a new queue consumer, more
  personal data handling, and the most work of the options (HLD, section 10).

** Option D: FourRealities mirrors every issue change in its own append-only log (product events)
- For: keeps history after deletion for every issue, not only at report time; could be hash-chained.
- Against: contradicts ADR-001 (FourRealities would copy Jira's facts as its own); storage and
  personal data grow with every edit on the site; product events can arrive late and can be missed,
  so the log is not complete; it duplicates LedgerSeal's role for the content that matters.

** Option E: Read the Jira audit log and add configuration events to the report
- For: one file with configuration and issue changes, closest to Auditor for Jira.
- Against: needs =manage:jira-configuration=, a scope that also allows changing Jira configuration;
  the data is already exportable natively by the same administrators; a high-risk scope for an
  evidence app.

| Option | N3 | N4 | N5 | N6 | N7 | New scope | New storage | Effort (HLD 10) |
|--------+----+----+----+----+----+-----------+-------------+-----------------|
| A | no | no | no | no | no | none | none | 0 |
| B | small projects | if signed | no | yes | no | none | none | about 8 days |
| C | yes | yes | yes, the report | yes | yes | none expected (spike S-1) | Object Store, KVS | about 23 days |
| D | yes | yes | yes, all issues | yes | yes | none | large, growing | above 30 days |
| E | yes, plus config | as C | as C | as C | as C | =manage:jira-configuration= | as C | C plus 3 days |

* Considered and excluded

| Capability | Why excluded | Where the need is met |
|------------+--------------+-----------------------|
| Administrative configuration audit log (the core of Auditor for Jira) | Forge apps get no event for most configuration changes; reading the Jira audit log needs =manage:jira-configuration= (Option E). | Jira audit log; organization audit log with Atlassian Guard |
| Issue view logging | Apps cannot see views. | Guard Premium or Cloud Enterprise user log ("Viewed Jira issue") |
| IP address per event | Forge gives apps no client IP. | Organization audit log |
| Mirroring all issue history for retention (Option D) | ADR-001; unbounded storage and personal data; incomplete by nature. | Jira keeps issue history; reports freeze what an audit needs |
| Restore of deleted issues | Not an evidence function; needs a full copy of issue content. | Backup apps; Jira admin process |
| Sending reports out: e-mail, webhooks, SIEM, S3, SFTP | No egress (Runs on Atlassian). | The user downloads the file |
| PDF reports | Needs a new dependency; a PDF cannot be rechecked by the verifier (LedgerSeal D-7). | JSON and CSV with a signed manifest |
| Copy of LedgerSeal or DefinitionGuard histories inside the report | Not readable across apps; one writer per fact (spec v3, invariant 1). | References by id and hash; LedgerSeal evidence export |
| Field values of free-text fields (Summary, Description, Environment, text area custom fields) | They can hold any personal or confidential data and can be large. The report records that the field changed, with the lengths, not the text (open question Q4). | The issue's History tab, as the user |
| Comment and attachment content | Same reason; not change-management evidence. | Jira |
| Electronic signature of an approval, 21 CFR Part 11 | Not this app (LedgerSeal listing, "Honest Compliance Boundary"). | A dedicated signing control |
| Confluence audit (Auditor for Confluence) | Jira only. | Confluence and Guard audit logs |
| Per-project retention settings | No customer asked; one site setting is simpler (ADR-013 deferred per-project settings for the same reason). | Site setting |
| Rewriting Jira history or locking issues | FourRealities never writes evidence other apps or Jira own. | LedgerSeal with =jira.issue.editable= (LedgerSeal spec v3, section 1) |

* Consequences

** Positive
- A migrating team can hand its auditor one signed file pair per project and period, with the gate
  evidence and the change history together, and the auditor can check it offline.
- The listing can name a concrete answer to "audit trail" without claiming to be a general Jira
  audit log.
- The record of the period stays after an issue is deleted, and the chain shows a deleted report.

** Negative
- New storage (Object Store, in Preview: "may be subject to shorter deprecation windows"); adding the
  =objectStore= module "triggers a major version upgrade", so each site administrator must accept
  the update.
- A new signing key to hold, rotate and publish (=docs/security/signing-key-rotation.md=).
- Reports hold change data from Jira (who changed what), so storage and personal data grow with use,
  bounded by the retention setting and the size limits.
- Forge storage is billed by use since 2026-01-01; the vendor pays for stored reports (Q6).
- FourRealities can only report what Jira's changelog holds: an issue deleted *before* a report was
  built is not in it. The report lists issues of the previous report that can no longer be read.

** Mitigations
- Spike S-1 proves the Object Store download from UI Kit before any other work; if it fails, the
  fallback (KVS chunks and a Custom UI download page) is costed in the HLD, section 10.
- The size limits and the issue cap stop a single report from exhausting time, memory or storage.
- Party tokens keep account ids out of the signed files, so erasure never breaks a signature.

* Open questions for the owner (decided 2026-11-08)
All decided as recommended; see "Owner decisions" above. Kept as asked, for the record.
- Q1. Approve Option C? (Recommended: yes.)
- Q2. Who may create reports: Tier 1 plus an "evidence report" group (recommended), or anyone with
  Browse projects?
- Q3. Default retention 400 days, range 90 days to 7 years? (Recommended: yes.)
- Q4. Free-text fields: record "changed" with lengths only (recommended), or include the text cut to
  500 characters?
- Q5. Accept Object Store (Preview) as the store, given the spike? (Recommended: yes, with the
  fallback costed.)
- Q6. Storage cost: cap stored reports per project (recommended: 200) and per file (50 MB)?
- Q7. Listing wording after approval: "evidence reports for change-management audits", never "audit
  log".
- Q8. May a Jira administrator delete a report before expiry, with a reason and a tombstone?
  (Recommended: yes.)
- Q9. Keep listing and download available when the licence is inactive, and stop only creation and
  schedules? (Recommended: yes.)
