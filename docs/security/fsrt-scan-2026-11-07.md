# FSRT scan of the four Jira apps, 2026-11-07

Ticket: AMS-76722, "DefinitionGuard: Enforced Definition of Done (systems.asymm.definitionguard)
has failed Custom-Check-Authorization-16711047855292326038 from FSRT", P2 Severe.

FSRT is Atlassian's open-source Forge Security Requirements Tester
(<https://github.com/atlassian-labs/FSRT>). This report states the rule that its authorization
check applies, the findings for each app before and after the fixes, and the evidence for each
result.

## 3. The rule: FSRT's authorization check

All paths are in the FSRT repository at the commit above.

### 3.1 Which code is checked

1. `ForgeModules::into_analyzable_functions` (`crates/forge_loader/src/manifest.rs`) marks a
   manifest function as invokable when a UI module names it as `function` or `resolver.function`.
   Examples: `jira:issuePanel`, `jira:projectPage`, `jira:projectSettingsPage`, `jira:issueContext`,
   `jira:issueAction`, `jira:globalPage`, the `resolver` of `jira:workflowValidator`.
2. Not invokable, so never checked for authorization: `scheduledTrigger`, `trigger` (events),
   the validator `function` of `jira:workflowValidator`, and `jira:adminPage`. For `jira:adminPage`
   the loader only sets an `admin` flag; it does not add a binding.
3. `scan_directory` (`crates/fsrt/src/main.rs`) runs `AuthZChecker` only when `func.invokable`.
   Web triggers get the authentication checker instead.
4. `Interp::run_checker` (`crates/forge_analyzer/src/interp.rs`) first checks the exported handler
   as a function. Only when the handler is not a function body (for example
   `export const handler = resolver.getDefinitions()`) does it look up each
   `resolver.define(name, callback)` and check every callback as its own entry point
   (`EntryKind::Resolver`, reported as `handler.<name>`).

### 3.2 Which calls are sensitive, and which count as a check

`FunctionAnalyzer::as_intrinsic`, `get_intrinsic` and `classify_api_call`
(`crates/forge_analyzer/src/definitions.rs`) classify a call when its callee is one of:

- `api.asApp().requestJira(...)` or `api.asUser().requestJira(...)`, with `api` the default import
  of `@forge/api` (also `requestConfluence`, `requestBitbucket`, `requestGraph`);
- `asApp().requestJira(...)` or `asUser().requestJira(...)` with `asApp` or `asUser` a named import
  of `@forge/api`;
- `requestJira(...)` imported by name from `@forge/api` or `@forge/bridge` (treated as not asApp);
- `graphqlGateway.compass.asApp().<fn>(...)` from `@atlassian/forge-graphql`.

`classify_api_call` then reads every string literal and template-literal text in the FIRST argument
(the route), and takes the highest of these kinds:

| The route text | Kind | Result |
|---|---|---|
| contains `permission` | Authorize | an authorization check, for asApp or asUser |
| matches `user`, `instance`, `avatar`, `license`, `preferences`, `serverInfo`, or contains `group` or `/wiki/api/v2/app/properties` | Trivial | safe |
| is exactly `/rest/api/3/field` or `/rest/api/2/field` | Fields | user field access (asUser), custom field (asApp) |
| contains `field` | CustomField | asApp: custom field access; asUser: safe |
| anything else | Unknown | asApp: **sensitive API call**; asUser: safe |

A call to `authorize` imported by name from `@forge/api` is also an authorization check.
So both `/rest/api/3/mypermissions` and `/rest/api/3/permissions/check` count, as the user or as the
app. Any other call made as the user is safe.

### 3.3 How the check flows

- `AuthorizeDataflow` and `AuthorizeState` (`No < CustomFieldOnly < Yes`) in
  `crates/forge_analyzer/src/checkers.rs`. After an Authorize call the state is `Yes`.
- Paths join with `max`. One path that reaches a check is enough; FSRT does not read the answer of
  the check. It tests that a check call is made, not that its result is used.
- A function's state at its return is its summary (`super_join_term` in `interp.rs`). A caller that
  calls a resolvable function takes that summary (`transfer_call`). So a helper that makes the
  check itself does count, when it is called directly.
- `AuthZChecker::visit_intrinsic` (`checkers.rs`) reports a sensitive asApp call reached with a
  state other than `Yes`, and stops that entry point at the first finding.
- The report (`impl IntoVuln for AuthZVuln`): check name `Custom-Check-Authorization-<hash>`, where
  the hash covers the source path from `src/` on, the entry point and the call stack; severity High;
  "Requirement 1.2". The hash does not depend on the machine.

### 3.4 What FSRT does not follow

These limits decide whether a real check is visible to it:

1. **Closures passed as arguments.** `lower_expr` lowers an arrow function used as a value to
   `undefined` (`Expr::Arrow(_) => Operand::UNDEF`, `definitions.rs`); its body becomes a separate
   anonymous function that no call reaches. So in
   `withRetry(() => api.asUser().requestJira(route\`.../mypermissions...\`))` the check is
   invisible, and so is an asApp call written the same way.
2. **A route in a variable.** `const path = route\`.../mypermissions...\`; requestJira(path)` has no
   literal in the first argument: kind Unknown, so as the user it is "safe", not a check.
3. **Calls through an object.** `requester.requestJira(...)`, `this.request(...)` and
   `(cond ? api.asUser() : api.asApp()).requestJira(...)` match no callee pattern and are not
   classified at all.
4. **Each function is walked once per scan.** `Interp::checker_visit` (`interp.rs`) records visited
   functions and is never cleared between entry points. With the stop at the first finding, only
   the first path into a shared helper is reported. Fixing that path can expose the next one.
5. **A wrapped handler.** When the exported handler is a function, for example
   `export const handler = async (event, context) => definitions(event, context)`, FSRT checks that
   function only (point 4 of 3.1) and never reaches the `resolver.define` callbacks.

## 4. DefinitionGuard

### 4.1 Before (master `e5b574c`, production 3.0.0)

FSRT reported one finding:

```
Custom-Check-Authorization-16711047855292326038 (High, Requirement 1.2)
Authorization bypass detected through handler.toggleItem in "src/index.ts".
Modules: [jira:issuePanel: definitionguard-issue-panel (resolver.function)]
Unauthorized API call via asApp() found via handler.toggleItem -> publishAttestation -> toggleChecklistItem
```

The asApp call is the issue property write in `publishAttestation`
(`src/integrity/attestation.ts`, `PUT /rest/api/3/issue/{id}/properties/definitionguard-dod`).

Was it real? The code did check permissions before it: `toggleChecklistItem` calls
`requireBrowseIssue` (Browse projects) and `getIssuePermissions` (Edit issues), both as the user
with `GET /rest/api/3/mypermissions`. But each check was written as
`fetchGranted(() => withRetry(() => api.asUser().requestJira(route\`...\`)), keys)`: a closure inside
a closure (limit 1). `hasTier1AdminPermission` held its route in a variable (limit 2). FSRT saw no
check, so under its rule the finding was correct for the code as written.

Two more findings were hidden by limit 4. Removing each reported resolver from a copy of master and
scanning again showed them:

| Step | Finding |
|---|---|
| 1 | `Custom-Check-Authorization-16711047855292326038`: `handler.toggleItem -> publishAttestation` |
| 2 (toggleItem removed) | `Custom-Check-Authorization-13168914673425698921`: `handler.resetChecklist -> publishAttestation` |
| 3 (resetChecklist removed) | `Custom-Check-Authorization-15837674219573298319`: `handler.waiveItem -> publishAttestation` |
| 4 (waiveItem removed) | none |

### 4.2 The fix (`feature/definitionguard-fsrt-authorization`)

- Every permission check now makes its call directly, as the user, with a literal route, in the
  checking function's own body:
  `res = await api.asUser().requestJira(route\`/rest/api/3/mypermissions?issueId=${issueId}&permissions=BROWSE_PROJECTS\`)`.
  Changed: `requireBrowseIssue`, `getIssuePermissions`, `getProjectPermissions`
  (`src/security/permissions.ts`), `isJiraAdmin`, `hasTier1AdminPermission`
  (`src/security/approver.ts`). The checks themselves (which permission, fail closed on any error)
  did not change.
- The 429 retry is kept: each call sits in a loop that ends with
  `if (!(await retryAfter(res, attempt))) break;`. `retryAfter` (`src/jira/jira-client.ts`) applies
  the same tries, waits and cap as `withRetry`.
- `fetchLiveJiraIssue` (`src/index.ts`) now reads the issue type and project as the user, not as
  the app. It runs only after the Browse projects check, so the user's own permission is enough.
- Calls that stay as the app, each after a check FSRT now sees, or outside FSRT's scope:

| Call (`src/...`) | Why as the app | Check before it |
|---|---|---|
| `integrity/attestation.ts` `publishAttestation`, issue property PUT | the signed record is the app's, not the user's | Browse projects plus Edit issues, waiver permission or approver (toggle, waive, reset); Administer projects or Jira admin (resync) |
| `settings/settings-resolvers.ts` `resyncIssues`, `/search/jql` | must find every open issue of the type, including issues hidden from the admin by issue security | `requireProjectAdmin` (Administer projects or Jira admin) |
| `settings/coverage.ts`, `/workflows/search` | needs the `read:workflow:jira` scope | `requireProjectAdmin` |
| `index.ts` validator: issue, status, changelog reads | a workflow validator runs with no user | not an FSRT entry point (3.1, point 2) |

### 4.4 Tests

`test/security/fsrt-authorization.test.ts`:

- For every resolver key of `handler`, `adminHandler` and `settingsHandler` (18 keys, all but the
  static `getAvailableTemplates`), called through the registered handler for a user whom Jira
  grants no permission: the resolver refuses (Browse denied, not admin, or template denied), reads
  and writes no app storage, makes no call as the app, and its only Jira call is the permission
  question as the user. A second test fails when a resolver key is added without a case.
- A user with Browse projects but without Edit issues cannot tick an item.
- Source rule: every `/mypermissions` call in `src` is a direct `await api.asUser().requestJira(route\`...\`)`
  and none is inside `withRetry(`. This keeps the checks in the form FSRT recognises.
- `retryAfter` unit tests.

`test/jira/jira-client.test.ts` (every Jira read retries a 429) accepts the inline loop.
`test/security/browse-check.test.ts` now expects the template read as the user.

Gate on the branch: `tsc --noEmit`, 35 suites and 484 tests with coverage thresholds, `npm run build`,
`npm audit --omit=dev --audit-level=high` (exit 0), `forge lint` (no issues). Deployed to

## 5. LedgerSeal, FourRealities, CascadePlan

All three scan clean with the default scanners and with secret-logging. No code was changed.

To learn whether FSRT walks their resolvers, a canary was added to a copy of each app: an unchecked
`api.asApp().requestJira(route\`/rest/api/3/issue/1\`)` called at the top of one resolver.

| App | Canary | FSRT |
|---|---|---|
| LedgerSeal | in `verify-issue-api` | reported (`handler.verify-issue-api -> fsrtCanary`) |
| FourRealities | in `getProjectDashboard` | reported (`handler.getProjectDashboard -> fsrtCanary`) |
| CascadePlan | in the shared resolver callback, and in a new direct `resolver.define` | not reported |

### 5.1 LedgerSeal and FourRealities

FSRT walks their resolvers, but none of their own asApp calls is in a form it classifies (limit 3):

- LedgerSeal passes `api.asApp()` and `api.asUser()` into `createJiraClient`
  (`src/index.ts` `forgeDeps`, `src/jira/jira-client.ts`), which calls `requester.requestJira(...)`.
- FourRealities picks the principal in `requestAs` (`src/accessor/default-forge-jira-issue-accessor.ts`):
  `(principal === 'user' ? api.asUser() : api.asApp()).requestJira(r, init)`, inside an arrow.

So FSRT's authorization rule has nothing to report in them, today or after a change that keeps
this form. The real checks (Browse projects as the user before any read as the app) are proven by
their own tests: `apps/ledgerseal/test/permission-checks.test.ts` and
`apps/fourrealities/test/manager/viewer-permissions.test.ts`.

### 5.2 CascadePlan

FSRT does not reach any CascadePlan resolver: `src/index.ts` exports
`handler = async (event, context) => definitions(event, backendContext)` (limit 5), and the admin
page is `jira:adminPage` (3.1, point 2). Even so, CascadePlan makes its Jira calls as the user:
`getJiraCaller` (`src/server/core.ts`) returns `withRetry(api.asUser())`. Its `asApp()` fallback runs
only when `api.asUser` is missing, which `@forge/api` never is. `test/reads-as-user.test.ts`
fails if any read uses asApp.

### 5.3 The admin pages of every app

FSRT does not check `jira:adminPage` resolvers in any app. DefinitionGuard's admin resolvers are
covered by the tests of section 4.4 (`adminHandler` cases).

## 6. False positives left

None. Nothing has to be argued in AMS-76722. A reply for the ticket can say: the reported path
(`handler.toggleItem -> publishAttestation`) checked Browse projects and Edit issues as the user
before the app wrote its issue property, but each check was made inside a closure, which FSRT does
not follow. In the new version every check is a direct `asUser()` call to
`/rest/api/3/mypermissions`, FSRT at `6c821bd` reports no finding, and CI now runs FSRT on every
push (section 7).
