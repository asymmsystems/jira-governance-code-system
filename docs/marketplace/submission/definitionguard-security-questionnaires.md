# DefinitionGuard: answers for the Marketplace security questionnaires (MK-02)

Answers for the owner to enter in the Developer Console. Nothing here has been submitted. Each answer names the code or the check that makes it true, so it can be checked again before submission.

- Question wording: the live "Forge" tab of the Forge app security questionnaire, as read from ECOHELP-182619 on 2026-11-06 (19 questions). The older numbering (Q1a, Q3, Q7 to Q13) from `docs/sdlc/cascadeplan-marketplace-review-2026-11/marketplace-research.md` section A.c is kept only as a cross-reference in the last column.
- Code described: branch `feature/definitionguard-permission-checks` (from master `6c19fa4`), which adds the Browse check of question 3, the issue property scope of question 7 and the input rules of question 9. It is deployed to the **development** environment only (Forge version 7.0.0, installation upgraded on asymmsystems.atlassian.net, 2026-11-06). The production build (DefinitionGuard 2.0.0, commit `c8be4c9`) does **not** have these changes; answer questions 3, 7 and 9 as below only after this branch is merged and deployed to production.
- The scope change makes the next production deploy a **major version**: `forge lint -e production` reports one approval, `MAJOR_VERSION_RULE` ("Change due to scope modification"); deploy with `forge deploy -e production --approve MAJOR_VERSION_RULE`, and each site administrator must accept the upgrade before the new version runs on their site.
- All paths below are under `apps/definitionguard/` unless they start with `.github/` or `docs/`.

It runs before any app storage read and before any `asApp()` call. A user without Browse projects gets "You need the Browse projects Jira permission on this issue to see its Definition of Done."; if Jira cannot answer (error, non-200, missing id), the resolver stops with "DefinitionGuard could not check that you can see this issue in Jira, so it shows nothing. The signing key is never logged: `signIfConfigured` logs only "DG_SIGNING_KEY is not set" or "not a usable Ed25519 key". Errors thrown out of a panel resolver (for example "Checklist item with id '<itemId>' not found on issue <key>") can appear in Forge's function logs; they hold an issue key and an item id, not personal data. The `console.error` in `src/frontend/index.tsx` runs in the user's browser. | Q8 |
| 9 | Controls to validate and sanitize all user inputs? | Yes | The issue and the project come from the Forge context only (`panelContext`, `src/index.ts`; `settingsContext`, `src/settings/settings-resolvers.ts`). Group search at most 100 characters (`MAX_QUERY_CHARS`), at most 20 groups. Every path is built with the `route` tag of `@forge/api`. The re-sync JQL (`resyncIssues`) is built from the context project id and an issue type id that must already have a stored template. | Q9 |

## 2. Evidence detail

### 2.1 Every `asApp` call

| File and function | Endpoint | Check before it |
|---|---|---|
| `src/index.ts`, `fetchLiveJiraIssue` (from `templateFor`) | `GET /rest/api/3/issue/{id}?fields=issuetype,project,status` | Browse projects on the issue as the user (`requireBrowseIssue`), at the start of every panel resolver. Runs only when the context lacks the project or issue type id. |
| `src/index.ts`, `fetchIssueForValidator` | `GET /rest/api/3/issue/{id}?fields=issuetype,project,assignee` | Validator: no user caller. |
| `src/index.ts`, `evaluateTransition` | `GET /rest/api/3/status/{id}` | Validator: no user caller. |
| `src/jira/assignee-history.ts`, `assigneeChanges(..., 'app')` | `GET /rest/api/3/issue/{id}/changelog` | Validator only. The panel calls it with `'user'`. |
| `src/settings/coverage.ts`, `gateCoverage` | `GET /rest/api/3/workflows/search?projectId=` | `requireProjectAdmin` as the user. |
| `src/settings/settings-resolvers.ts`, `resyncIssues` | `GET /rest/api/3/search/jql` (id and key of the project's open issues of one type) | `requireProjectAdmin` as the user. |
| `src/integrity/attestation.ts`, `publishAttestation` | `PUT /rest/api/3/issue/{id}/properties/definitionguard-dod` | The calling action's permission check as the user (question 3). |
