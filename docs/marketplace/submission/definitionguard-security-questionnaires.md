## Open issues

1. **Question 3 (blocking): one `asApp()` read runs before the user's permission check.** `fetchLiveJiraIssue` (`src/index.ts`) reads `GET /rest/api/3/issue/{id}?fields=issuetype,project,status` as the app. `templateFor` calls it only when the Forge context lacks the project id or the issue type id, to choose the checklist template. It is reached from `getChecklist` (no permission check at all), and from `toggleItem` and `waiveItem` before their permission checks (through `currentState`). The result is used only to pick a template; no issue field is returned to the user, but the template for that issue type is. In addition, the panel's read resolvers `getChecklist`, `getHistory` and `getEvidence` return stored checklist data (item states, waiver reasons, evidence links and notes, who acted) for the issue in the Forge context with no permissions REST check that the user may browse it. Those are app storage reads, not `asApp()` calls, but they rest on the same trust in the Forge context. Recommended fix: one `GET /rest/api/3/mypermissions?issueKey=<key>&permissions=BROWSE_PROJECTS` as the user (the helper `getIssuePermissions` in `src/security/permissions.ts` already does this call) at the start of every panel resolver, before `templateFor`.
2. **Question 7 (least privilege): `write:jira-work` is broader than needed.** The app's only Jira write is its own issue property `definitionguard-dod` (`publishAttestation`, `src/integrity/attestation.ts`; `grep -rn "method: '" src` finds one `PUT`). The granular scope `write:issue.property:jira`, which LedgerSeal uses, would cover it. Changing a scope makes the next production deploy a major version that each site administrator must accept. Either change the scope, or answer "Yes" with the justification in the table and keep this item open.
3. **Question 9 (input validation), minor gaps.** `itemId` (toggle, waive, evidence) is turned into text with no length or character check; it is only compared with the template's item ids, and an unknown id is refused, but the refusal message repeats it (`statusEntry`, `src/domain/event-log.ts`). The history `cursor` (`getChecklistHistory`) is any text and goes to Forge storage as a query cursor. Group ids in `setApproverPolicyFlow` (`src/security/policy-admin.ts`) have no length limit (Jira administrators only). Recommended fix: `itemId` against `^[A-Za-z0-9_-]{1,64}$` (the rule `validateTemplate` already applies to item ids), a length limit on the cursor and on group ids.
4. **Key custody outside the app (question 13 context).** The production signing key is held by Forge as an encrypted variable. A plain copy (`~/.keys/definitionguard/dg-prod-2026-11.key`, PKCS#8 PEM, not passphrase-encrypted, file mode 600, directory mode 700; checked 2026-11-06 without reading the key) is on the owner's workstation. The runbook (`docs/sdlc/definitionguard-marketplace-fixes-2026-11/progress-log.md`, section "Owner commands", step 2) says to store it offline. This does not change the answer to question 13, which is about the app.
