## Open issues

1. **Question 3: fixed** (`cfe2cba`). Every resolver that acts on the context issue now checks the user's permission with the permissions REST API, as the user, before any `asApp()` call: `verify-issue-api` (also used by the issue context entry), `seal-issue-api`, `revoke-seal-api`, `seal-history-api` and `seal-evidence-api` each start with `browseDenied` (`src/service/ledger.ts`), which calls `GET /rest/api/3/mypermissions?issueId=<id>&permissions=BROWSE_PROJECTS` as the user (`canBrowseIssue`, `src/jira/jira-client.ts`). Without the permission, or when Jira answers 403 or 404, the resolver answers `NO_BROWSE_PERMISSION` ("You do not have permission to browse this issue in Jira, so LedgerSeal shows nothing about it.", shown in the panel); any other failure of the check answers `JIRA_UNREACHABLE`. In both cases it reads nothing as the app, writes nothing and returns nothing about the issue. Proof: `test/permission-checks.test.ts` (each resolver: refused with no app read and no storage write; fail closed when the check fails; unchanged with the permission); removing the check from any one resolver makes its three tests fail. The three admin resolvers already checked global Administer Jira as the user first and make no issue read; the validator and the triggers have no calling user (section 2.1).
2. **Question 8: fixed** (`90522f7`). The seven `console.error` calls that logged a whole error object (the earlier text said six; section 2.2 lists seven, because `verifyIssueFlow` has two) now call `logFailure` (`src/service/log.ts`), which writes only the error's name, code and HTTP status, never its message, stack or the object. Proof: `test/log-safety.test.ts` makes each of the seven places fail with an error whose message holds a secret and checks that every log argument is text without it; reverting any one place makes its test fail.
3. **Key custody outside the app (question 13 context).** The production signing key is held by Forge as an encrypted variable. Two plain copies of the private key are on the owner's workstation: `~/.keys/ledgerseal/ls-prod-2026-11.key.pem` (PKCS#8, not passphrase-encrypted) and `~/.keys/ledgerseal/ls-prod-2026-11.key.b64` (the base64 value given to Forge); files mode 600, directory mode 700 (checked 2026-11-06 without reading the key). The runbook (`docs/sdlc/ledgerseal-marketplace-fixes-2026-11/progress-log.md`, section "Owner commands", step 3) says to move it to the company password manager or an encrypted offline copy and then shred the plain file; that step is not marked done. This does not change the answer to question 13, which is about the app.

## 2. Evidence detail

### 2.1 Every `asApp` and `asUser` call

All Jira calls go through `createJiraClient(asApp, asUser)` in `src/jira/jira-client.ts`. `forgeDeps(asUser)` (`src/index.ts`) passes `api.asUser()` for resolvers and `null` for the validator and the triggers (so every as-user method returns `FORBIDDEN` there and the action fails closed).

| Method | Endpoint | Runs as | Permission check before it |
|---|---|---|---|
| `getIssue` | `GET /rest/api/3/issue/{id}?fields=*all,-comment` | app | Every issue resolver: `canBrowseIssue` as the user; seal and revoke also `isApprover` as the user. Validator, trigger: none possible (no user). |
| `getComments` | `GET /rest/api/3/issue/{id}/comment` (paged) | app | Same as `getIssue`. Evidence: restricted comments then also checked as the user. |
| `getWorklogs` | `GET /rest/api/3/issue/{id}/worklog` (paged) | app | Same as `getIssue`. Evidence: restricted work logs then also checked as the user. |
| `getFields` | `GET /rest/api/3/field` | app | Site metadata, not issue data. |
| `getChangelog` | `GET /rest/api/3/issue/{id}/changelog` (paged) | app | Same as `getIssue`. |
| `getUserName`, `accountState` | `GET /rest/api/3/user?accountId=` | app | Display names of people already named on the issue or in the record; account state for the personal data job. |
| `putSealProperty` | `PUT /rest/api/3/issue/{id}/properties/ledgerseal-cert` | app | Written on seal and revoke (after `isApprover`), and when a change is recorded (`recordIncidentIfNew`, from verify, the validator or the trigger). The property holds only ids, hashes, status, counts and the signature (`buildAttestation`). |
| `canBrowseIssue` | `GET /rest/api/3/mypermissions?issueId=&permissions=BROWSE_PROJECTS` | user | It is the check; first call of every issue resolver. |
| `getIssueScope` (code signing) | `GET /rest/api/3/issue/{id}?fields=project,issuetype` | app | `canBrowseIssue` as the user (code request); seal and revoke also `isApprover`. Read only when a code-signing policy is on. |
| `notifyUser` (code signing) | `POST /rest/api/3/issue/{id}/notify`, `to.users` = the caller only | app | `canBrowseIssue` and the approver check as the user, the project is a code-signing project, the caller is not locked out and within the rate limits (`requestCodeFlow`). As the app because Jira refuses a notification whose only recipient is the calling user (spike S-8). |
| `getProjects` (code signing) | `GET /rest/api/3/project/{keyOrId}` | user | After `isJiraAdmin` (admin page). |
| `hasApproverPermission` | `GET /rest/api/3/mypermissions?issueId=&permissions=ADMINISTER_PROJECTS,ADMINISTER` | user | It is the check. |
| `getMyGroupIds` | `GET /rest/api/3/myself?expand=groups` | user | It is the check. |
| `isJiraAdmin` | `GET /rest/api/3/mypermissions?permissions=ADMINISTER` | user | It is the check. |
| `findGroups`, `getGroups` | `GET /rest/api/3/groups/picker`, `GET /rest/api/3/group/bulk` | user | After `isJiraAdmin`. |
| `getVisibleCommentIds`, `getVisibleWorklogIds` | comment and work log lists | user | They are the visibility checks. |

### 2.2 Every backend log call

| File and function | What is written |
|---|---|
| `src/jira/jira-client.ts`, `pages` | `LedgerSeal: more than 5000 <comments or worklogs>; the issue is too large to check` |
| `src/jira/jira-client.ts`, `readChangelog` | the same text for change log entries, with the numeric issue id |
| `src/index.ts`, `onIssueDeleted` | numeric issue id and a count; on failure the numeric issue id and the error's name, code and status |
| `src/index.ts`, `personalDataReport` | counts; on failure a fixed text and the error's name, code and status |
| `src/domain/attestation.ts`, `signerFromEnvironment` | fixed text: the key could not be read as an Ed25519 key |
| `src/service/ledger.ts`, `writeAttestation` | `UNSIGNED_LOG` (names the variables, not their values) and the numeric issue id; or "could not write the ledgerseal-cert property on issue <id>" |
| `src/service/ledger.ts`, `sealIssueFlow` | "could not delete the replaced snapshot of issue <id>" and the error's name, code and status |
| `src/service/ledger.ts`, `verifyIssueFlow` (two calls) | "verify failed" and the error's name, code and status |
| `src/service/ledger.ts`, `issueChangedFlow` | "issue event handling failed" and the error's name, code and status |
| `src/service/ledger.ts`, `evidenceFlow` | `UNSIGNED_LOG` and the numeric issue id |
| `src/service/conversion.ts` (weekly conversion loop) | "could not convert the record of issue <id>" and the error's name, code and status |

Each failure line is written by `logFailure` (`src/service/log.ts`): `LedgerSeal: <what>: <name> code=<code> status=<status>`. The name and code are kept only when they are plain identifiers, so an error's message, stack or values never reach the logs (Open issue 2).
